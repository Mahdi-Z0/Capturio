<objective>

## Goal

Determine why desktop capture delivers roughly 12 fps regardless of the requested frame rate, and
either raise it materially or establish with evidence that it is an Electron/Chromium limitation on
this platform.

## Purpose

Laggy motion is the user's primary complaint, and three prior fixes missed it: bitrate (H.264 was
discarding the hint), codec (VP9 honours bitrate but changed nothing about motion), and the capture
scaler (fixed sharpness, not smoothness). Measurement in 01-01 showed capture delivers ~12.2 fps
whether 30 or 60 is requested, and identically with and without an encoder attached — so the
encoder is not the bottleneck and the frame-rate request is being ignored.

A quality picker built on top of a 12 fps pipeline would be polish on a broken foundation. This is
the higher-value fix.

## Output

- A repeatable, committed benchmark script (not a scratchpad throwaway)
- Measured results for each capture configuration tried
- Either an applied fix, or a documented platform limit with the evidence behind it

</objective>

## AC-1: The benchmark separates source render rate from capture delivery rate

```gherkin
Given a benchmark that displays animated content and captures the screen
When it runs
Then it reports the animation's own achieved rAF rate AND the capture delivery rate as separate numbers
And a case where the animation itself is the bottleneck is distinguishable from a capture-pipeline limit
```

**Why this is AC-1:** the 01-01 measurement used a full-screen canvas drawing 40 rects per frame as
the motion source. If that animation only rendered at ~12 fps, the capturer was faithfully
delivering every frame that existed, and the "12 fps capture limit" is an artifact of the test
rather than a real defect. This must be ruled out before anything else is concluded.

<!-- audit-added: M1 — the confound test needs a decision rule, or AC-1 is unfalsifiable -->

**Decision rule (required).** A capture measurement is only admissible when the motion source
sustains **at least twice the target capture rate** during the run. For a 30 fps target the source
must hold ≥ 60 rAF fps.

- Source ≥ 2× target and delivery well below target → the capture pipeline is the limit. Valid.
- Source below 2× target → **inconclusive**. Record it as inconclusive and make the source cheaper
  before drawing any conclusion. Do not report such a run as evidence of a capture limit.

If the source cannot be made fast enough to clear the bar, say so plainly rather than reporting a
number that cannot distinguish the two causes.

## AC-2: Capture configurations are tested and recorded with numbers

Given the benchmark from AC-1

## AC-3: The outcome is conclusive either way

```gherkin
Given all configurations have been measured
When the results are compared
Then either a configuration materially improves delivered fps (>= 24 fps sustained on real motion)
  and is applied to the app
Or the evidence shows no configuration helps, and the limitation is documented in CLAUDE.md
  with the measured numbers and the configurations ruled out
And a negative result is treated as a valid, complete outcome — not a failure to be retried
```

<!-- audit-added: M2 — "sustained" must be defined statistically or the AC is unmeasurable -->

**"Sustained" means per-window, not mean.** Delivered fps must be computed per 2-second window
across the run, and the criterion is the **minimum** window, not the average. A run that delivers
40 fps for two seconds and 8 fps for eight seconds averages 14.4 and would read as a partial win,
while feeling worse than a steady 15. Perceived smoothness is destroyed by the dips, so the dips
are what the threshold governs.

Report for every run: minimum window fps, median window fps, and the mean. If the minimum window
is below 24 the configuration has not met AC-3, whatever its average says.

<!-- audit-added: M4 — control for system load -->

**Baseline control.** System load varies between runs; this session has twice had orphaned Electron
processes competing for CPU. Re-measure the **default configuration** immediately before and after
each candidate, and report all three. A candidate only counts as an improvement when it beats both
adjacent baselines. If the two baselines differ by more than 20% from each other, the machine was
not in a steady state and the whole triple is discarded and re-run.

## AC-6: A long recording stays bounded in memory (carried from 01-01 AC-6)

```gherkin
Given a recording running for at least 5 minutes
When it is still in progress
Then renderer memory use does not scale with duration
And stopping still produces a single playable file
```

<!-- audit-added: S1 — "does not scale" needs a measurement method or it is unfalsifiable -->

**Measurement method (required).** Sample the renderer process's private working set via
`process.getProcessMemoryInfo()` (or `performance.memory.usedJSHeapSize` as a fallback) every 15
seconds and record the series. The criterion is that memory at minute 5 is within **1.5×** of
memory at minute 1. Anything approaching linear growth with duration means chunks are being
retained and the streaming path has a leak.

<!-- audit-added: S2 — this plan deliberately creates a large file on the user's disk -->

**Free space precheck.** At 20 Mbps a 5-minute recording is roughly 750 MB, and the configuration
sweep adds more. Check available space on the target volume before starting and refuse with a clear
message if under 3 GB. Delete the long test recording after verifying it, unless the user asks to
keep it. 01-01's audit deferred a free-space check on the grounds that nothing yet created large
files; this plan does, so the deferral no longer holds for the benchmark path.

  <action>
    Create `scripts/bench-capture.mjs`, runnable via the project's Electron binary. Promote the
    throwaway scratchpad harnesses into one maintained script, because this measurement will be
    needed again whenever Electron or the capture path changes.

    It must:
    - Render a motion source whose own frame rate is measured and reported. Count its rAF
      invocations and report achieved rAF fps alongside capture fps. Keep the drawing cheap
      (a few moving rects, not a full-screen per-pixel repaint) so the source is not the limiter.
    - Report, per run: requested fps, negotiated fps, source rAF fps, delivered capture fps,
      encoded size, and whether an encoder was attached.
    - Count delivered frames at real time via `requestVideoFrameCallback` on a video element fed by
      the capture stream. Do NOT count during accelerated playback — at playbackRate > 1 the display
      refresh caps the count and the number is meaningless.
    - Accept a configuration name as an argument so each variant runs in a fresh process. Chromium
      feature flags must be set before app ready, so they cannot be switched within one run.
    - Write results as JSON to a path given on the command line.
    - Exit non-zero and print a readable message on failure. A previous harness printed
      `[object Object]` and hung for 400s, which wasted a full cycle. Serialize errors as
      `err.stack || err.message || String(err)`.

    <!-- audit-added: M3 — benchmark output must not pollute the user's real recordings -->

      on the command line, defaulting to the OS temp directory. The benchmark must **never** write
      into `app.getPath('videos')/ScreenRecorder`. That folder holds the user's real recordings, and
      a sweep of a dozen configurations would bury them in test files that look like recordings.
    - Delete its own artifacts on exit unless `--keep` is passed.

    <!-- audit-added: M2 — per-window statistics -->
    - Record per-2-second-window delivered fps, and report min / median / mean. A single average
      hides the dips that actually break perceived smoothness.

    <!-- audit-added: S5 — keep the repo's quality gates green -->
    - `scripts/` is new and is not covered by either tsconfig. Either add it to the lint config with

    Avoid: leaving orphaned Electron processes. Always `app.exit()`, stop all tracks, and register a

## AUDIT-ENFORCED INVARIANTS (carried from 01-01)

- The renderer never holds the full recording in memory
- No recording is written directly to its final filename
- No existing file is ever overwritten
- The display source is selected by `display_id` correlation, never `sources[0]` alone
- Every IPC handler taking a path validates containment

## SCOPE LIMITS

- No quality picker — that is 01-03, and it should be built on a capture pipeline that performs
- No audio, no window/region selection, no library UI
- No native modules and no bundled ffmpeg in this plan. If the findings point there, that is a
  separate decision, not a quiet escalation inside a research plan.
- No new runtime dependencies

<!-- audit-added: invariants protecting the integrity of the research itself -->

## AUDIT-ENFORCED INVARIANTS

A research plan's failure mode is a false conclusion, not a crash. These protect the conclusion:

- No capture measurement is admissible unless the motion source sustained ≥ 2× the target rate.
- No configuration is declared a winner on a single run, or without adjacent baselines.
- AC-3 is judged on the **minimum** 2-second window, never the mean.
- Benchmark artifacts never touch the user's recordings directory.
- OS-level settings are never changed without explicit user consent.
- A negative result is reported as a result. Absence of a fix is never presented as a fix, and
  "no configuration helped" is a complete outcome rather than a reason to keep going.

</boundaries>
