<objective>

## Goal

Give the user a single quality control with three coherent presets, persisted across restarts and
applied to the next recording — and close the three acceptance criteria that have now survived two
plans untested.

## Purpose

This is the feature the user asked for at 01-01's checkpoint and which has been deferred twice, each
time for a defensible reason: 01-01's boundaries excluded a settings screen, and 01-02 found that
capture frame rate was the higher-value problem. Both reasons are now spent. The pipeline performs,
so a quality control is no longer polish over a defect.

The second half matters more than it looks. AC-5, AC-6 and AC-7 have been listed as acceptance
criteria in two consecutive plans and exercised in neither. Carrying them a third time would make
them decoration.

## Output

- A quality preset control on the main screen, defaulting to High
- `settings.json` in `app.getPath('userData')`, owned by main
- Memory instrumentation that makes AC-6 measurable rather than assumed
- Dev-only simulation hooks that make AC-5 and AC-7 testable at all

</objective>

<acceptance_criteria>

## AC-1: The preset persists across restarts

```gherkin
Given the user selects the "Maximum" preset
When the app is closed and reopened
Then "Maximum" is still selected
And the setting is stored in app.getPath('userData')/settings.json, not in the recordings folder
```

## AC-2: The selected preset actually changes the recording

```gherkin
Given the "Balanced" preset (30 fps, 8 Mbps) is selected
When a recording is made of high-motion content
Then the captured track reports a 30 fps target
And the encoder ceiling is 8 Mbps rather than 20

Given the "Maximum" preset (60 fps, 40 Mbps) is selected
When the same content is recorded
Then the captured track reports a 60 fps target
And the resulting file is materially larger than the Balanced recording of the same content
```

The second half matters: a setting that is stored and displayed but never reaches `MediaRecorder`
would satisfy a naive check while doing nothing.

<!-- audit-added: M2 — Balanced reintroduces a defect the user just had fixed -->

## AC-2b: The Balanced preset warns about the motion it costs

```gherkin
Given the user is choosing a preset
When they consider "Balanced"
Then its description states that 30 fps makes motion less smooth, not only that files are smaller
And "High" is presented as the recommended default
```

**Why this is release-blocking.** Balanced drops to 30 fps, which is exactly the setting whose
interval jitter produced the "ball snapping between positions" complaint — it took five rounds of
investigation to find and fix. Offering it labelled only "Smaller files" ships a switch that
silently reintroduces a known, hard-won defect, with no hint of the cost. A user who picks it will
reasonably report the bug again.

Either the description carries the tradeoff honestly, or Balanced should not ship.

## AC-3: The preset cannot be changed mid-recording

```gherkin
Given a recording is in progress
When the user looks at the quality control
Then it is visibly disabled and cannot be changed
And the recording continues with the preset it started with
```

<!-- audit-added: S5 — 'recording' is not the only non-idle state -->

Disable on **any** status other than `idle`, not only `recording`. The hook also has `starting` and
`saving` states; a change landing during `starting` would race the constraint read, and one during
`saving` would imply it affected a recording that is already finished.

## AC-4: A missing or corrupt settings file does not break the app

```gherkin
Given settings.json is absent, empty, malformed JSON, or contains an unknown preset name
When the app starts
Then it falls back to the High preset without crashing
And the invalid file is rewritten with valid defaults immediately on detection
```

<!-- audit-added: S2 — "replaced on next write" has no trigger -->

The original wording said the invalid file would be replaced "on the next successful write". If the
user never changes the preset, that write never happens, so a corrupt file is re-read and re-failed
on every launch forever. Rewrite it at detection time instead.

## AC-5: Failed capture acquisition leaves the UI idle (third listing — must close)

```gherkin
Given capture acquisition fails or is denied
When the failure reaches the renderer
Then the UI returns to idle showing a readable error
And no file and no .part file is left in the recordings folder
```

**Why this has never been tested.** It was written twice against a permission prompt the user could
cancel. This app installs `setDisplayMediaRequestHandler`, which auto-grants, so no prompt has ever
appeared — the user correctly reported not recognising the step. Task 2 adds a dev-only simulation
hook so the failure path can actually be exercised.

## AC-6: A long recording stays bounded in memory (third listing — must close)

```gherkin
Given a recording running for at least 5 minutes
When memory is sampled every 15 seconds via app.getAppMetrics()
Then the median of the last minute's samples is within 1.5x of the median of the first minute's
And the sampled series is written to the console so the claim is checkable, not asserted
And stopping still produces a single playable file
```

<!-- audit-added: M1 — the metric must identify the right process, or it measures nothing -->

**Process identification is release-blocking.** `app.getAppMetrics()` returns every process in the
app — main, GPU, utility, and one renderer per window, plus another when DevTools is open. Sampling
"the renderer" without pinning it down could track the GPU process or a DevTools window and report a
flat, meaningless series. Since the checkpoint explicitly asks the user to open DevTools for AC-5
and AC-7, a second renderer **will** be present.

Resolve the recording window's OS process id via `webContents.getOSProcessId()` and match metrics on
`pid`. If no metric matches that pid, log that the sample failed rather than silently recording zero.

<!-- audit-added: S4 — single samples are noise -->

**Compare windowed medians, not single samples.** A single reading at minute 1 may land before the
first major GC or mid-allocation, and one at minute 5 may land just after a collection. Either makes
the ratio arbitrary. Use the median of each minute's four samples.

**Why this has never been tested.** The audit specified `getProcessMemoryInfo()` sampling and it was
never wired up, so "memory does not scale" stayed an assumption across two plans. Task 1 instruments
it.

## AC-7: Capture ending outside the app is handled (third listing — must close)

```gherkin
Given a recording is in progress
When the video track ends without the user pressing Stop
Then the recording is finalized and saved
And the UI returns to idle showing the saved file
```

**Why this has never been tested.** It was written against Chromium's "Stop sharing" bar, which this
app never shows. `track.onended` is implemented but has only ever fired in theory. Task 2's dev hook
ends the track directly.

<task type="auto">
  <name>Task 1: Settings persistence and memory instrumentation in main</name>
  <files>src/shared/types.ts, src/main/index.ts</files>
  <action>
    **Preset model** — define in `src/shared/types.ts` first, per the CLAUDE.md sync rule:

    ```
    QualityPreset = 'balanced' | 'high' | 'maximum'
    QUALITY_PRESETS: Record<QualityPreset, { label, frameRate, videoBitsPerSecond, blurb }>
      balanced: 30 fps,  8_000_000  — "Smaller files. Good for static screens."
      high:     60 fps, 20_000_000  — "Default. Smooth motion, sensible size."
      maximum:  60 fps, 40_000_000  — "Best quality. Large files."
    ```

    Values come from 01-02's measurements. 60 fps is the default because it halves interval jitter
    versus 30; Balanced drops to 30 only to make files smaller, which is the single legitimate
    reason to want it.

    **Persistence** in `src/main/index.ts`:
    - `settings.json` in `app.getPath('userData')`. Not the recordings folder: that is the user's
      media, and config does not belong in it.
    - `settings:get` returns the stored preset, or `'high'` when the file is absent, empty,
      unparseable, or names an unknown preset. Never throw from the read path — a corrupt config
      must not prevent the app from starting (AC-4).
    - `settings:set` validates the value against the known preset keys before writing, and writes
      atomically (temp file + rename), reusing the same reasoning as the recording write path: a
      power loss mid-write must not leave a half-written config that then fails every start.

    <!-- audit-added: M3 — concurrent writes tear the config -->
    - **Serialize writes.** Clicking through presets quickly fires overlapping `settings:set` calls.
      With a fixed temp filename, two in-flight writes share one temp file and race: one rename can
      fail, or rename a file the other is still writing. Either chain writes through a single
      promise queue, or give each write a unique temp name. A torn settings file is exactly the
      corruption AC-4 then has to recover from — do not create the problem the fallback exists for.

    <!-- audit-added: S6 — cheap now, expensive later -->
    - Include a `version: 1` field in the written JSON. Adding fields later without it means guessing
      at the shape of old files.

    <!-- audit-added: S2 — heal a corrupt file when it is found -->
    - When the read path rejects a file as absent/unparseable/unknown-preset, immediately write a
      valid default file. Otherwise a corrupt config is silently re-read and re-rejected forever.

    **Memory instrumentation** (AC-6):
    - While at least one recording is active, sample `app.getAppMetrics()` every 15s. Record the
      renderer process's `workingSetSize`.
    - On `recordings:finish`, log the series plus first/last/peak and the ratio of last to first.
      This is what makes AC-6 checkable instead of asserted.
    - Sampling must stop when no recording is active. A timer left running is a leak of its own.

    Avoid: storing settings in localStorage (renderer-owned state contradicts the architecture
    rule), and writing config anywhere under the recordings directory.
  </action>

  <done>AC-1 (storage), AC-4 (fallback), AC-6 (instrumentation) satisfied on the main side</done>

  <files>src/preload/index.ts, src/renderer/src/useRecorder.ts</files>
  <action>
    **Preload** — add `getQuality(): Promise<QualityPreset>` and
    `setQuality(p: QualityPreset): Promise<void>`, typed from shared. Keep the explicit named
    surface; never expose `ipcRenderer`.

    **useRecorder** — read the preset before acquiring capture and apply both halves of it:
    - `frameRate: { ideal: preset.frameRate }` in the capture constraints
    - `videoBitsPerSecond: preset.videoBitsPerSecond` in the `MediaRecorder` options

    Replace the module-level `FRAME_RATE` and `VIDEO_BITS_PER_SECOND` constants with preset lookup.
    Read the preset at `start()`, not at module load, so a change applies to the next recording
    without a restart. Expose the active preset on the hook's return so the UI can show what a
    recording is actually using.

    **Dev-only simulation hooks** — the reason AC-5 and AC-7 have never been exercised is that
    neither failure has a user-reachable trigger in this app. Under `import.meta.env.DEV` only,
    attach to `window`:
    - `__sim.failCapture()` — makes the next `start()` reject as if acquisition failed (AC-5)
    - `__sim.endTrack()` — ends the active video track without pressing Stop (AC-7)

    <!-- audit-added: S1 — a sticky test flag is worse than no test flag -->
    `failCapture()` must be **one-shot**: arm it, consume it on the next `start()`, and clear it
    whether that start succeeded or failed. A latched flag means every subsequent recording fails
    with no visible cause, and the user — who was told to type this into a console — has no way to
    connect the two. Log clearly when the simulated failure fires, so it is never mistaken for a
    real defect.

    These must be entirely absent from production builds; guard them so Vite strips them. They are
    test affordances, not features, and must not appear in the UI.

    Avoid: applying the preset to a recording already in progress — the preset is captured at start
    and held for the duration (AC-3).

<boundaries>

## DO NOT CHANGE

- The streaming save pipeline (`recordings:begin` / `append` / `finish` / `abort`) — Phases 2-4
  depend on this contract
- `.part` → rename atomic write, and `recoverOrphanedParts()`
- The capture path: `getDisplayMedia` with `resizeMode: 'none'`, no width/height constraints
- `webPreferences` — `contextIsolation: true`, `nodeIntegration: false`
- `package.json` — no `"type": "module"`; `typescript` pinned at 5.9.3
- Codec preference (webm/vp9 first) — changing it would silently disable bitrate control

## SCOPE LIMITS

- Quality preset only. No settings screen, no other preferences.
- No audio of any kind.
- No window or region selection.
- No recordings library, browse list, or delete UI.
- No new runtime dependencies.
- 60 fps stays the default. Balanced exists for file size, not because 30 is otherwise preferable.

<!-- audit-added: invariants specific to shipping a user-facing setting -->

## AUDIT-ENFORCED INVARIANTS (01-03)

- A preset that degrades a previously-fixed behaviour must say so where it is chosen. Never label a
  known regression with only its upside.
- A stored setting is not a working setting. Prove it reached the encoder, in the output.
- Test-only hooks are one-shot and absent from production builds.
- Config writes are serialized and atomic. The fallback path exists for external corruption, not
  for corruption this app caused itself.

## AUDIT-ENFORCED INVARIANTS (carried from 01-01)

- The renderer never holds a whole recording in memory
- No recording is written directly to its final name
- No existing file is ever overwritten
- Every IPC handler taking a path validates containment
