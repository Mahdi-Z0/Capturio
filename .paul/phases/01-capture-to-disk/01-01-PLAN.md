<objective>

## Goal

Record the primary screen with no audio, and write a playable video file to
`<Videos>/ScreenRecorder/` with a timestamped name.

## Purpose

This is the narrowest slice that forces the three decisions everything else in the project depends
on: how the capture stream is obtained, which container/codec the recorder produces, and where
files are written. Getting these wrong is expensive to reverse once window selection, region
cropping, and audio mixing are layered on top.

## Output

- A working record/stop control in the renderer
- A saved, playable file in the user's Videos folder
- The IPC surface (`shared` → `main` → `preload`) that Phase 2's library will build on

</objective>

## AC-1: Recording starts on the primary screen with no picker

```gherkin
Given the app is running and no recording is in progress
When the user clicks Record
Then the primary screen begins capturing without any source-picker dialog appearing
And the UI switches to a recording state showing elapsed time
```

## AC-2: Stopping writes a playable file to the Videos folder

```gherkin
Given a recording is in progress
When the user clicks Stop
Then a video file is written to <Videos>/ScreenRecorder with a timestamped filename
And that file opens and plays correctly in Windows Media Player
And the file is never written beside the application executable
```

## AC-3: The app reports where the recording went

```gherkin
Given a recording has just been saved
When the save completes
Then the UI displays the saved filename and its folder
And a control is offered that reveals the file in Explorer
```

## AC-4: A failed capture does not leave the UI stuck

```gherkin
Given the user denies or cancels the screen capture request
When the capture promise rejects
Then the UI returns to the idle state and shows a readable error
And no zero-byte file is written to the recordings folder
```

## AC-5: A failed write surfaces, and leaves no partial file

```gherkin
Given a recording is in progress
When the write to disk fails (disk full, permission denied, file locked)
Then the UI shows a readable error naming the failure
And no partial or truncated file remains in the recordings folder
And the failure is written to the main-process error log
```

## AC-6: A long recording does not grow unbounded in memory

```gherkin
Given a recording has been running for 20 minutes at full screen resolution
When the recording is still in progress
Then encoded data has been streamed to disk incrementally rather than accumulated in memory
And renderer memory use does not scale with recording duration
And stopping still produces a single playable file
```

## AC-8: Recordings are legible at the display's native resolution

```gherkin
Given the primary display is running at its native resolution
When a recording is made of screen content containing small UI text
Then the saved file is encoded at approximately 16 Mbps, not the 2.5 Mbps default
And the captured frame size matches the display's physical pixel dimensions
And the frame rate is 30 fps
And small text in the played-back recording is legible rather than smeared
```

**Why this was missed:** the original plan specified no bitrate, resolution, or frame rate, so all
three fell to Chromium defaults. `MediaRecorder` defaults to 2.5 Mbps and that default does not
scale with resolution — a 4K capture receives the same 2.5 Mbps as a 480p one. AC-2 only required
that the file "plays correctly", which it did. The enterprise audit did not catch this either: it
reviewed integrity and failure handling but never asked whether the artifact is good.

## AC-7: Capture ending outside the app is handled

```gherkin
Given a recording is in progress
When the capture track ends without the user clicking Stop
  (the OS "Stop sharing" control, a display being disconnected, or a revoked permission)
Then the recording is finalized and saved rather than left running
And the UI returns to idle showing the saved file
```

<task type="auto">
  <name>Task 1: Main process — recordings directory, save/reveal IPC, and auto-selected display source</name>
  <files>src/shared/types.ts, src/main/index.ts</files>
  <action>
    First reconcile `src/shared/types.ts`. The existing `RecorderApi` interface declares methods
    that do not exist (`listRecordings`, `deleteRecording`). Trim it to exactly the Phase 1 surface
    so shared/main/preload stay in sync per the CLAUDE.md rule. Keep the `Recording` type but drop
    `durationMs` if it is not populated in this phase — do not declare fields the code never sets.

    In `src/main/index.ts`:
    - Add `getRecordingsDir()` returning `join(app.getPath('videos'), 'ScreenRecorder')`, created
      with `mkdirSync(..., { recursive: true })` on first use. Never derive this path from
      `__dirname` or `app.getAppPath()` — MSIX installs read-only and the app must not write beside
      its executable.
    - Register `session.defaultSession.setDisplayMediaRequestHandler`. Resolve sources via
      `desktopCapturer.getSources({ types: ['screen'] })` and return the primary screen with
      `{ video: source, audio: false }`. This is what makes AC-1's "no picker" behaviour work.
      Audio stays `false` in this phase.

    <!-- audit-added: M2 — primary-display correlation (must-have) -->
    - Do NOT use `sources[0]`. Source order is not guaranteed to put the primary display first, so
      `sources[0]` makes AC-1 wrong on multi-monitor setups. Correlate explicitly: read
      `screen.getPrimaryDisplay().id` and select the source whose `display_id` matches it, comparing
      as `String(display.id) === source.display_id`. Electron documents `display_id` as possibly an
      **empty string** when unavailable — in that case fall back to `sources[0]` and log that the
      correlation failed. If `getSources` returns an empty array, call `callback(null)` so
      `getDisplayMedia` rejects cleanly rather than hanging (feeds AC-4).

    <!-- audit-added: M1 — streaming writes replace single-buffer save (must-have) -->
    - Replace the single `recordings:save` channel with a streaming trio. Buffering the whole
      recording in memory and shipping one ArrayBuffer over IPC costs at least three full copies
      (Blob → ArrayBuffer → structured clone → Buffer) and fails on long recordings and on Electron's
      IPC message-size ceiling. Every later phase inherits this contract, so it must be right now:
        - `recordings:begin` → `(ext: string)`: resolve a timestamped path, open a write stream to a
          temporary `<name>.part` file, return an opaque `recordingId`.
        - `recordings:append` → `(recordingId: string, chunk: ArrayBuffer)`: append to that stream.
          Reject unknown ids. Respect stream backpressure — await `drain` rather than queueing
          unboundedly.
        - `recordings:finish` → `(recordingId: string)`: close the stream, `fs.promises.rename` the
          `.part` file to its final name, and return the `Recording`. The rename is what makes the
          write atomic, so a crash mid-recording leaves a `.part` file rather than a corrupt
          recording that looks valid (AC-5).
        - `recordings:abort` → `(recordingId: string)`: close and delete the `.part` file. Called
          when capture fails (AC-4).
      On any stream error, destroy the stream, delete the `.part` file, and reject with a message
      naming the cause. Never resolve a save that did not fully write.

    <!-- audit-added: M4 — filename collision (must-have) -->
    - Timestamps to the second collide on rapid start/stop and would silently overwrite a recording.
      Open the `.part` file with `flag: 'wx'` and, on `EEXIST`, retry with a `-2`, `-3` … suffix.
      Never overwrite an existing file.

    - Add IPC handler `recordings:reveal` accepting a path and calling `shell.showItemInFolder`.
      <!-- audit-added: S3 — separator-aware containment -->
      Containment must be separator-aware: compare `path.resolve(input)` against
      `path.resolve(recordingsDir) + path.sep`. A bare `startsWith` on the directory string also
      accepts sibling paths such as `...\ScreenRecorder-evil\x.mp4`. Reject anything outside.
    - Add IPC handler `recordings:dir` returning the recordings directory path.

    <!-- audit-added: S5 — quit during recording -->
    - On `before-quit`, finalize any open write stream (close + rename) before allowing exit. Losing
      an in-progress recording because the user closed the window is silent data loss.

    <!-- audit-added: S6 — diagnosability -->
    - Log every rejected IPC call and every stream failure via `console.error` with the channel name
      and the error. A personal app needs no audit trail, but a save that fails with no trace is
      undiagnosable.

    Avoid: writing the file from the renderer, and passing `ipcRenderer` across the bridge.
  </action>
  <verify>`npm run typecheck` passes; `npm run build` succeeds; a forced stream error leaves a `.part` file and no final file</verify>
  <done>AC-1 (primary correlation), AC-5 (atomic write + error path), AC-6 (streaming) satisfied on the main side</done>
</task>

<task type="auto">
  <name>Task 3: Renderer — record/stop control and MediaRecorder pipeline</name>
  <files>src/renderer/src/useRecorder.ts, src/renderer/src/App.tsx</files>
  <action>
    Create `useRecorder.ts` encapsulating the recording lifecycle:
    - Pick the container at runtime with `MediaRecorder.isTypeSupported()`, in order:
      `video/mp4;codecs=avc1`, then `video/webm;codecs=vp9`, then `video/webm`. Derive the file
      extension from whichever wins. Do not hardcode a container — CLAUDE.md requires the runtime
      check, and Store-friendly mp4 is preferred when available.
    - Acquire the stream with `navigator.mediaDevices.getDisplayMedia({ video: true, audio: false })`.
      Main's request handler supplies the primary screen, so no picker appears.
    <!-- audit-added: M1 — stream chunks instead of buffering (must-have) -->
    - Call `mediaRecorder.start(timeslice)` with a timeslice of 2000ms so `ondataavailable` fires
      periodically. On each chunk, `await chunk.arrayBuffer()` and forward it via
      `window.api.appendChunk`. Do NOT accumulate chunks in an array — that is the unbounded-memory
      path AC-6 forbids. Serialize appends (await each before sending the next) so chunks cannot
      arrive out of order.
    - Call `beginRecording(ext)` before `mediaRecorder.start()`, and `finishRecording(id)` from
      `onstop`. On any failure after begin, call `abortRecording(id)` so no `.part` file is orphaned.
    - Always stop every track on the stream when recording ends or errors, so the capture indicator
      clears and the screen is released.
    <!-- audit-added: S2 — externally terminated capture (strongly recommended) -->
    - Attach `onended` to the video track. When it fires, finalize exactly as a user Stop would
      (AC-7). The user can end capture from the OS "Stop sharing" control or by disconnecting a
      display, and without this the UI keeps showing a recording that is no longer capturing.
    <!-- audit-added: S5 — concurrent start guard -->
    - Guard `start()` against re-entry: if status is not `idle`, return immediately. A double-click
      on Record must not open two MediaRecorders writing to two `.part` files.
    - Expose `{ status, elapsedMs, lastSaved, error, start, stop }`. Surface rejection from
      `getDisplayMedia` as a readable error and return to idle without saving (AC-4), and surface
      write failures the same way (AC-5).

    Rewrite `App.tsx` around this hook: a primary Record/Stop control, elapsed time while recording,
    and a saved-file line with a "Show in folder" action calling `revealRecording`. Keep the source
    list from the scaffold only if it still earns its place; this phase's screen is the record
    control, not a source browser.

    Avoid: writing files from the renderer, importing Node modules, and adding new dependencies.
  </action>

## AUDIT-ENFORCED INVARIANTS

These came out of the enterprise audit and must not be traded away during APPLY:

- The renderer never holds the full recording in memory. Chunks stream to main as they arrive.
- No recording is ever written directly to its final filename. Always `.part` → `rename`.
- No existing file is ever overwritten. `wx` flag, then suffix on collision.
- The display source is selected by `display_id` correlation, never `sources[0]` alone.
- Every IPC handler that takes a path validates containment before acting on it.
- No save resolves successfully unless the bytes were fully written and the rename succeeded.
