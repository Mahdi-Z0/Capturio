<objective>

## Goal

Fill the library's reserved tile areas with a frame from each recording, cached so it is decoded
once rather than on every launch — and close the four defensive acceptance criteria that 02-01
implemented but never exercised.

## Purpose

The tiles currently show empty rectangles, which is the least useful possible grid: every recording
looks identical, so the only way to tell them apart is by timestamp. A thumbnail is what makes a
visual library worth having over a plain list.

The second half matters more. Four criteria from 02-01 shipped implemented-but-untested, and STATE
records this as the **third** plan with that pattern. Defensive code that has never run is not
protection; it is an assumption. 01-03 showed the cure — dev-only hooks made two long-carried
criteria testable in minutes. This is the last plan in the phase, so it is the last chance to close
them before the phase transitions.

## Output

- A frame from each recording, shown in its tile
- A thumbnail cache in `userData` that survives restarts and prunes itself
- `scripts/verify-guards.cjs`, an automated check of the protocol handler's refusals
- Dev-only hooks that make the remaining defensive paths reachable

</objective>

<acceptance_criteria>

## AC-1: Each recording shows a frame from itself

```gherkin
Given the library lists recordings
When a tile becomes visible
Then it shows a frame taken from that recording
And the frame is not the very first one, which is usually black or half-drawn
And a recording whose frame cannot be decoded keeps its placeholder rather than showing a broken image
```

<!-- audit-added: S1 — "all thumbnails are black" would pass a casual look -->

```gherkin
Given two recordings with visibly different content
When both thumbnails are generated
Then their image bytes differ
```

If the seek silently fails, every thumbnail becomes frame 0 — usually black — and the grid looks
plausible at a glance while being useless. Comparing two generated thumbnails is a cheap check that
catches it; eyeballing a dark grid does not.

## AC-2: Thumbnails are decoded once, not every launch

```gherkin
Given a recording's thumbnail has been generated
When the app is closed and reopened
Then the tile shows its thumbnail without decoding the video again
And the cached image lives in app.getPath('userData'), never in the recordings folder
```

## AC-3: The cache is a cache, not an index

```gherkin
Given the thumbnail cache directory is deleted while the app is closed
When the app is reopened
Then the library still lists every recording correctly
And thumbnails regenerate on demand
And nothing is lost except the time to re-decode

Given a recording is deleted
When the app next starts
Then its orphaned cache entry is removed
```

<!-- audit-added: M2 — "cannot read the folder" is not "everything was deleted" -->

```gherkin
Given the recordings folder cannot be read — an external drive is disconnected,
  or a permissions error occurs
When pruning runs at startup
Then pruning is skipped entirely and the reason is logged
And no cache entry is removed
```

**Why this is release-blocking.** Pruning decides what to delete by asking which sources still
exist. If the folder read fails, every source looks absent and the naive implementation wipes the
whole cache. It destroys no user data, but it is a self-inflicted failure that is invisible until
someone wonders why every thumbnail regenerated. Treat an unreadable folder as "unknown", never as
"empty".

**This is the load-bearing criterion.** The project decided against an index file because an index
drifts from the filesystem and needs migrating. A cache is only legitimate while deleting it costs
nothing but time. If any part of the library ever *depends* on the cache existing, it has become an
index and this criterion has failed.

## AC-4: A changed file gets a new thumbnail

```gherkin
Given a recording has a cached thumbnail
When the file is replaced with different content at the same path
Then the cache key changes, because it includes size and modified time
And the tile shows a frame from the new content, not the old one
```

## AC-5: Generation does not make the library feel slow

```gherkin
Given a folder with many recordings
When the library opens
Then the list renders immediately with placeholders
And thumbnails fill in progressively, at most 2 decodes at once
And only tiles that are on screen are decoded
And scrolling is not blocked while decoding happens
```

Two concurrent decodes, not the four used for duration probes: a thumbnail decode also seeks and
paints, so it costs more than reading metadata.

## AC-6: The empty state is actually seen (02-01 AC-2, unexercised)

```gherkin
Given the recordings folder contains no recordings
When the library renders
Then the empty state appears, naming how to make a first recording
And no error, spinner, or blank panel is shown
```

## AC-7: A failed Recycle Bin move is proven not to escalate (02-01 AC-5b, unexercised)

```gherkin
Given shell.trashItem is made to fail
When a delete is attempted
Then the app reports the failure
And the file is still present afterwards
And no permanent deletion occurred
```

## AC-8: An in-flight recording is proven undeletable (02-01 AC-5c, unexercised)

```gherkin
Given a recording is in progress
When a delete is requested for the file it is writing
Then the delete is refused
And the recording completes and plays normally
```

## AC-9: The protocol handler's refusals are proven (02-01 AC-8, partial)

```gherkin
Given the recording protocol handler
When it receives a name containing a separator, a `..` sequence, a percent-encoded traversal,
  a drive letter, a UNC prefix, a `.part` extension, or an unknown extension
Then every one of them is refused
And the refusals are asserted by an automated script, not by inspection
```

<!-- audit-added: M1 — a test of a copied implementation proves nothing -->

**The script must exercise the real validation code, not a reimplementation.**
`registerRecordingProtocol()` lives inside `src/main/index.ts` and is not exported, and importing
that module starts the whole application. The path of least resistance is for
`verify-guards.cjs` to contain its own copy of the checks — which would pass while the shipped
handler diverged, and is worse than no test because it manufactures confidence.

Extract the decision into a pure, exported function — `resolveRecordingRequest(name)` returning
either a resolved absolute path or a refusal reason — in a module both the handler and the script
import. The handler becomes a thin wrapper that maps a refusal to a 404. The test then asserts
against the same code that runs in production.

```gherkin
Given verify-guards.cjs
When it evaluates a hostile input
Then it calls the same exported function the protocol handler calls
And no validation logic is duplicated between the two
```

<task type="auto">
  <name>Task 1: Thumbnail cache in main</name>
  <files>src/shared/types.ts, src/main/index.ts, src/preload/index.ts</files>
  <action>
    Types first in `src/shared/types.ts`, per the CLAUDE.md sync rule.

    **Cache location and key.** A `thumbnails/` directory under `app.getPath('userData')`. Never the
    recordings folder — that holds the user's media. The key is a hash of
    `fileName + size + mtimeMs`, so replacing a file at the same path produces a different key and
    the stale image is never shown (AC-4).

    **IPC:**
    - `thumbs:get` — `(filePath)`. Returns a `data:` URL when cached, or `null`. `data:` is already
      permitted by `img-src 'self' data:`, so no CSP change is needed and none should be made.
      Validate containment with the shared helper before touching anything.
    - `thumbs:put` — `(filePath, jpegBytes: ArrayBuffer)`. Writes the cache entry atomically
      (temp + rename), the same reasoning as every other write in this app. Reject payloads over a
      sane ceiling (256 KB) — this handler is callable from the renderer and should not accept
      arbitrary quantities of data.

      <!-- audit-added: M3 — do not write unvalidated renderer bytes to disk -->
      **Check the bytes are actually a JPEG** (`FF D8 FF` magic, and a `FF D9` tail) before writing.
      Size alone does not make content valid: this handler accepts renderer-supplied bytes and
      writes them to the user's profile, then serves them back with a `image/jpeg` data URL. A
      mislabelled payload would be stored and re-served as something it is not. Reject and log
      anything that fails the check.

      <!-- audit-added: S5 — bound the cache -->
      Cap total cache size at 64 MB. On exceeding it, delete the least-recently-modified entries
      until under the cap. An unbounded derived-data directory in a user profile is untidy at best
      and surprising at worst.
    - `thumbs:prune` — remove entries whose source recording no longer exists. Run at startup,
      alongside `recoverOrphanedParts()`.

    **The cache must stay disposable (AC-3).** Nothing outside thumbnail display may read it. The
    library list, playback, delete and duration must all keep working with the directory deleted.
    If a future change makes any of those depend on it, the cache has become an index.

    Avoid: storing anything but the image bytes. No durations, no names, no ordering — the moment
    the cache holds authoritative metadata it stops being disposable.
  </action>
  <verify>`npm run typecheck`; delete the thumbnails directory and confirm the library still lists, plays and deletes</verify>
  <done>AC-2, AC-3, AC-4 satisfied on the main side</done>
</task>

<task type="auto">
  <name>Task 2: Generate and show thumbnails</name>
  <files>src/renderer/src/Library.tsx, src/renderer/src/index.css</files>
  <action>
    Load `frontend-design` before changing tile appearance.

    Extend the existing `useDurations` machinery rather than adding a second observer — it already
    tracks which tiles are visible and bounds concurrency. Rename it to reflect that it now probes
    both duration and thumbnail.

    For a visible tile with no cached thumbnail:
    - Ask main for a cached one first. Only decode on a miss.
    - Decode via a detached `<video>` at the protocol URL. **Seek before capturing**: a recording's
      first frame is usually black or mid-draw. Seek to `min(1s, 10% of duration)` and wait for
      `seeked` before painting.
    - Paint to a canvas at tile size (around 320×180), export as JPEG at ~0.7 quality. JPEG, not
      PNG: a screen-content PNG at this size is several times larger for no visible gain in a
      thumbnail.

      <!-- audit-added: S3 — assert the canvas size, not only the byte ceiling -->
      **Set the canvas dimensions explicitly and assert them.** A canvas left at the video's natural
      size produces a full-resolution JPEG — likely 200 KB or more, close enough to the 256 KB
      ceiling that it would pass the size check while filling the cache with full frames. The byte
      cap is a backstop, not the control.

    <!-- audit-added: S4 — reuse the existing dedupe -->
    - Reuse the per-path `queued` set that the duration probe already maintains, so a tile scrolling
      in and out does not queue the same recording repeatedly.
    - Send the bytes to `thumbs:put`, then show the result.
    - Tear the element down afterwards, as the duration probe already does.
    - **At most 2 concurrent decodes** (AC-5). A decode seeks and paints; it is heavier than reading
      metadata.
    - On any failure, keep the placeholder. A recording that cannot be decoded — such as the early
      fragmented mp4s — must not show a broken image or an error (AC-1).

    Tile appearance: the thumbnail fills the reserved area, which is already sized, so nothing
    should reflow. Keep the placeholder visible underneath while loading rather than collapsing the
    space.

    Avoid: decoding tiles that are not visible, and blocking the list render on any of this.
  </action>
  <verify>`npm run lint`, `npm run typecheck`, `npm run build`; thumbnails appear progressively and scrolling stays responsive</verify>
  <done>AC-1, AC-5 satisfied</done>
</task>

  <action>
    Four criteria shipped in 02-01 without ever running. Close them.

    **`scripts/verify-guards.cjs`** — an Electron script that registers the real protocol handler
    and asserts it refuses each hostile input, then exits non-zero if any is served (AC-9):
    - `../secret.txt`, `..%2f..%2fsecret.txt`, `%252e%252e%252fsecret.txt`
    - `sub/dir/file.webm`, `sub\\dir\\file.webm`
    - `C:/Windows/System32/drivers/etc/hosts`
    - `\\\\server\\share\\file.webm`
    - `Recording-x.webm.part`
    - `notes.txt`
    Also assert a legitimate filename with mixed case **is** served, so the test proves the handler
    still works rather than merely refusing everything. Add an npm script `verify:guards`.

    **Dev-only hooks**, guarded by `import.meta.env.DEV` in the renderer and stripped from
    production, following the one-shot pattern established in 01-03:
    - `__sim.emptyLibrary()` — make the next list render as empty, so the empty state can be seen
      without moving the user's files (AC-6).
      <!-- audit-added: S2 — intercept in the renderer, not main -->
      **Intercept in the renderer**, after `listRecordings()` returns. A main-side flag would be a
      production-reachable way to make the library appear empty, which is a worse outcome than the
      criterion is worth. The renderer path still exercises the real empty-state rendering, which is
      what AC-6 is actually about.
    - `__sim.failTrash()` — make the next `trashItem` reject, one-shot, to prove the delete path
      reports rather than escalating (AC-7)

    The main-side flag for `failTrash` must be dev-only as well; a production build must contain no
    way to reach it.

    **AC-8** needs no hook: start a recording, then call `deleteRecording` on its in-flight path from
    the console. The handler already refuses it; the point is to watch it refuse.

    Avoid: a hook that latches. 01-03's audit found that a sticky failure flag breaks every
    subsequent operation with no visible cause.

<boundaries>

## DO NOT CHANGE

- **The CSP.** Thumbnails use `data:`, already permitted by `img-src 'self' data:`. `file:` remains
  forbidden, and `recording:` stays scoped to `media-src` — do not extend it to `img-src`.
- The protocol handler's validation rules. Task 3 tests them; it does not relax them.
- Streaming save pipeline, `.part` atomic write, `recoverOrphanedParts()`
- Capture path, codec preference, quality preset model
- `webPreferences` — `contextIsolation: true`, `nodeIntegration: false`
- `package.json` — no `"type": "module"`; `typescript` pinned at 5.9.3

## SCOPE LIMITS

- No rename, trim, tagging, search, or filter.
- No audio, no window or region selection.
- No index or database. The cache holds images only.
- No new runtime dependencies. No ffmpeg.
- No change to how the list itself is produced — 02-01 owns that.

## AUDIT-ENFORCED INVARIANTS (02-02)

- **A test must exercise shipped code.** No validation logic is duplicated between the handler and
  its verifier. A green test of a copy is worse than no test.
- **"Cannot read" is never "does not exist."** Pruning, and any other delete-by-absence logic,
  skips rather than assumes.
- **Renderer-supplied bytes are validated before they touch disk**, by content and not only size.
- **The cache stays disposable.** Nothing outside thumbnail display may read it.

## AUDIT-ENFORCED INVARIANTS (carried)

- Every handler taking a path validates containment, separator-aware
- A failed safe-delete never becomes an unsafe one
- Test-only hooks are one-shot and absent from production builds
- Destructive actions default to recoverable
