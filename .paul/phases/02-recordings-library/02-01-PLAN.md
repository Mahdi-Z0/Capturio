<objective>

## Goal

Let the user see every recording they have made, play one without leaving the app, open it in the
system player if they prefer, and delete it safely.

## Purpose

This is the second half of the project's core value — "find, play, or delete the result without
leaving the app". Phase 1 made recordings; nothing in the app has ever shown them. It is also the
only remaining feature path that does not depend on the blocked window-capture work.

## Output

- A library view listing every recording in the recordings folder
- Inline playback, and an "open in default player" action
- Delete to the Recycle Bin, with a permanent option
- Grid tiles ready for the thumbnails that 02-02 will fill

</objective>

<acceptance_criteria>

## AC-1: Every recording in the folder is listed

```gherkin
Given the recordings folder contains files
When the library opens
Then each recording appears with its name, creation date, file size and duration
And the newest appears first
And a file added or removed outside the app is reflected on refresh, because the list is read
  from the folder rather than from an index
```

## AC-2: An empty library explains itself

```gherkin
Given the recordings folder is empty or absent
When the library opens
Then it shows an empty state that says how to make a recording
And it does not show an error, a spinner, or a blank panel
```

## AC-3: A recording plays inside the app

```gherkin
Given a recording is listed
When the user selects it
Then it plays inline with working play/pause, scrubbing, volume and fullscreen
And playback goes through the app's own protocol handler
And no file:// URL is ever constructed, and `file:` is never added to the CSP
```

**Amended 2026-09-17 after the boundary stop.** As written this AC required playback to work with
`media-src 'self' blob:` unchanged. That is not achievable: `'self'` means the document's origin, and
a custom scheme is a different origin, so the CSP blocked the handler no matter how correct it was.
Measured both ways — blocked with the original list, plays cleanly with `recording:` added. The user
authorised adding `recording:`; `file:` remains forbidden, which is the distinction the original
wording was reaching for.

## AC-4: A recording can be opened in the system player

```gherkin
Given a recording is listed
When the user chooses "Open in default player"
Then Windows opens it in the user's associated application
And the app stays open and usable
```

## AC-5: Delete goes to the Recycle Bin by default

```gherkin
Given a recording is listed
When the user deletes it
Then the file moves to the Recycle Bin rather than being destroyed
And it disappears from the library
And it can be restored from the Recycle Bin

Given the user explicitly chooses the permanent option
When they confirm
Then the file is unlinked and cannot be restored
And the difference between the two actions is obvious before either is taken
```

<!-- audit-added: M2 — a failed trash must never become a permanent delete -->

## AC-5b: A failed Recycle Bin move never becomes a permanent delete

```gherkin
Given shell.trashItem fails — a network drive, a filesystem without a Recycle Bin,
  or a volume where it is disabled
When the user deletes a recording
Then the app reports that the file could not be moved to the Recycle Bin
And the file is left exactly where it was
And the app does NOT fall back to permanent deletion
```

**Why this is release-blocking.** `trashItem` rejects on several real Windows configurations. A
fallback to `unlink` would look like a helpful recovery while doing the one thing the user chose
the Recycle Bin to avoid — and they would only discover it when trying to restore. Failing visibly
is correct; escalating silently is data loss dressed as robustness.

<!-- audit-added: M3 — never delete a file that is being written -->

## AC-5c: A recording currently being written cannot be deleted

```gherkin
Given a recording is in progress
When a delete is requested for the file that recording is writing to
Then the delete is refused with a readable reason
And the in-flight recording continues unaffected
```

The list excludes `.part` files, so this is not reachable through normal UI use — but the IPC
handler is reachable regardless of what the UI offers, and a delete landing mid-write would corrupt
an active recording. Check the in-flight map, not just the file extension.

## AC-6: Deleting the recording that is playing does not break the app

```gherkin
Given a recording is currently playing inline
When that same recording is deleted
Then playback stops cleanly
And the library returns to its list state without an error or a stuck player
```

## AC-7: A file that disappears externally is handled

```gherkin
Given a recording is listed
When the file is deleted or moved outside the app and the user then plays or deletes it
Then the app reports that the file is no longer there and refreshes the list
And it does not crash, hang, or leave a broken entry
```

## AC-8: The library cannot reach outside the recordings folder

```gherkin
Given any library operation that takes a path — play, delete, reveal, open
When the path resolves outside the recordings directory
Then the operation is refused and logged
And the containment check is separator-aware, so a sibling folder sharing the name prefix
  is also refused
```

<!-- audit-added: M1 — the protocol handler is the app's only file-serving surface -->

**The custom protocol needs its own rules, not just "validate the path".** It is the one surface
that serves file bytes to renderer content, and it will be reachable from any URL the renderer can
construct — including one built from a recording's own name. Specify and implement all of:

- The request carries a **single path segment**, never a path. Reject anything containing `/`, `\`,
  `..`, a drive letter, or a leading `\\` (UNC).
- **Decode before validating, once.** `%2e%2e%2f` must be rejected, and double-decoding must not be
  performed at all — decode exactly once, then validate the result.
- Resolve against the recordings directory and run the same separator-aware containment check as
  the other handlers. Resolution comes after decoding, never before.
- Serve only files whose extension is a known recording container (`.webm`, `.mp4`). A `.part`
  file must never be served: it is mid-write, and a torn read looks like a corrupt recording.
- Reject anything else with a 404-equivalent rather than an error that reveals the filesystem
  layout.

```gherkin
Given the protocol handler receives a request
When the requested name contains a separator, a traversal sequence, or an unexpected extension
Then the request is refused and logged
And no bytes from outside the recordings directory are ever served
```

  <name>Task 1: Main — enumerate, play, delete, open</name>
  <files>src/shared/types.ts, src/main/index.ts</files>
  <action>
    Types first in `src/shared/types.ts`, per the CLAUDE.md sync rule. Extend `Recording` with
    `durationMs` and `modifiedAt`, or add a `RecordingListItem` if that keeps the save path's
    `Recording` honest — do not declare fields the save path never sets.

    In `src/main/index.ts`:

    - `recordings:list` — read the folder, stat each file, return newest first. Skip `.part` files:
      they are in-flight or unrecovered, not library content. Return an empty array for a missing
      folder rather than throwing (AC-2).

    - **Duration.** `stat` cannot supply it. Read it in the renderer from the `<video>` element's
      `loadedmetadata`, and let the list render without a duration until it arrives. Do not block
      the whole list on decoding every file — that is what makes a library feel slow.

      <!-- audit-added: S2 — unbounded metadata probes will not scale -->
      **Bound the concurrency.** One `<video>` per recording, all loading at once, means a folder of
      100 recordings opens 100 simultaneous decodes. Probe at most 4 at a time, and only for items
      that are visible. Tear each element down after reading `duration` — leaving them attached
      holds decoders open for files the user never plays.

    - **Playback protocol.** Register a custom scheme in main and serve recordings through it. The
      renderer CSP is `media-src 'self' blob:`, so `file://` cannot load, and loosening the CSP to
      allow arbitrary local files is the wrong trade for a video player. Register with
      `protocol.registerSchemeAsPrivileged` before app ready (`stream: true`, `supportFetchAPI: true`)
      and handle it with `protocol.handle`. Resolve the requested name **inside the recordings
      directory only** — this handler is reachable from renderer content, so treat its input as
      untrusted (AC-8).

    - `recordings:delete` — `(filePath, permanent: boolean)`. Default path uses
      `shell.trashItem` so a mis-click stays recoverable. `permanent: true` uses `unlink`. Validate
      containment before either.

      <!-- audit-added: M2 -->
      **If `trashItem` rejects, surface the failure and stop.** Do not fall back to `unlink`. A
      silent escalation to permanent deletion defeats the entire reason the Recycle Bin is the
      default (AC-5b).

      <!-- audit-added: M3 -->
      **Refuse if the target is being written.** Check the in-flight `active` map before deleting;
      a delete landing mid-write corrupts a live recording. The `.part` exclusion in the list is a
      UI convenience, not a guarantee — this handler is callable regardless of what the UI shows
      (AC-5c).

    <!-- audit-added: S3 — "newest first" needs a defined key -->
    - Sort by **modified time**, not birth time. A recovered recording was renamed from `.part`, so
      its birth time predates the content while its mtime reflects when writing finished. State the
      chosen key in the code so it is not silently swapped later.

    - `recordings:open-external` — `shell.openPath`, containment validated.

    - Reuse the existing separator-aware containment check from `recordings:reveal` rather than
      writing a second one. Four handlers now take a path; one shared helper is the only way they
      stay consistent.

    Avoid: returning absolute paths the renderer then passes back unchecked, and any handler that
    trusts its input because "only our UI calls it".

<boundaries>

## DO NOT CHANGE

- Streaming save pipeline: `recordings:begin` / `append` / `finish` / `abort`
- `.part` atomic write and `recoverOrphanedParts()`
- Capture path: `getDisplayMedia`, `resizeMode: 'none'`, 60 fps target
- Codec preference (webm/vp9 first)
- Quality preset model and `settings.json` handling from 01-03
- `webPreferences` — `contextIsolation: true`, `nodeIntegration: false`
- **The renderer CSP must not be loosened — with one authorised exception.**
  The boundary fired as written: `media-src 'self' blob:` blocked the custom protocol, because
  `'self'` is the document origin and `recording://` is a separate one. Execution stopped, the
  options were measured, and the user authorised adding **`recording:`** on 2026-09-17.
  **`file:` remains forbidden.** That is what the boundary exists to prevent, and the distinction
  is the whole point: `recording:` reaches one validated handler, `file:` reaches the filesystem.
- `package.json` — no `"type": "module"`; `typescript` pinned at 5.9.3

## SCOPE LIMITS

- No thumbnails. That is 02-02; this plan only reserves the space for them.
- No rename, no trim, no tagging, no search or filter.
- No audio work, no window or region selection.
- No index or database. The list is read from the folder every time.
- No new runtime dependencies.

<!-- audit-added: invariants for a plan that deletes data and serves files -->

## AUDIT-ENFORCED INVARIANTS (02-01)

- **A failed safe-delete never becomes an unsafe one.** If the Recycle Bin is unavailable, stop and
  say so. Never substitute permanent deletion for a recoverable one.
- **The protocol handler serves recordings, not files.** Single segment, decoded once, extension
  allow-listed, containment-checked. It never serves a `.part`.
- **Never delete what is being written.** Check the in-flight map, not the filename.
- **A refresh is not a reset.** Background updates must not interrupt what the user is watching.

## AUDIT-ENFORCED INVARIANTS (carried)

- Every handler taking a path validates containment, separator-aware
- No recording is ever overwritten
- Destructive actions default to recoverable
