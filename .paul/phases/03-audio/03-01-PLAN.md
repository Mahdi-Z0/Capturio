<objective>

## Goal

Record the sound the computer is playing, alongside the picture — selectable before recording,
persisted between runs, and never at the cost of losing the recording if audio is unavailable.

## Purpose

Audio is 11 of the 16 remaining feature points and this plan is the first 4 of them. It is next
because window capture is blocked at 1.1 fps, and because a screen recording without sound is
useless for the most common reason people record a screen: showing someone how something works.

## Output

- An audio-source control offering "No audio" and "Computer audio"
- The choice persisted alongside the quality preset
- Recordings that carry a real system-audio track
- A clear, non-fatal path when loopback is unavailable

</objective>

<acceptance_criteria>

## AC-1: Computer audio is actually recorded

```gherkin
Given "Computer audio" is selected
When a recording is made while sound is playing
Then the saved file contains an audio track
And playing it back reproduces that sound
```

Verified by listening, and by confirming the saved file reports an audio track — not by trusting
that the constraint was accepted.

## AC-2: "No audio" means no track, not a silent one

```gherkin
Given "No audio" is selected
When a recording is made
Then the saved file contains no audio track at all
```

A muted or silent track is not the same thing: it wastes space, and some players show audio
controls for a file that can never produce sound. CLAUDE.md specifies omitting the track entirely.

## AC-3: The choice persists and is applied at start

```gherkin
Given "Computer audio" is selected
When the app is closed and reopened
Then "Computer audio" is still selected
And the setting is stored alongside the quality preset in userData

Given a recording is in progress
When the audio control is examined
Then it is disabled, exactly as the quality control is
```

## AC-4: A settings file written before audio existed still loads

```gherkin
Given a settings.json written by 01-03, containing only version 1 and a quality preset
When the app starts
Then it loads without error, keeping the stored quality
And the audio mode defaults to "No audio"
And the file is rewritten at version 2 with both fields
```

The current file on disk is version 1. Bumping the schema without handling it would either crash
the read path or silently reset the user's quality preset.

## AC-5: Audio failure never costs the recording

```gherkin
Given "Computer audio" is selected but loopback cannot be provided —
  no audio device, a driver refusing capture, or the handler failing
When the user presses Record
Then the recording still starts and captures video
And the UI states plainly that audio could not be captured
And the saved file is a valid video-only recording
```

**This is the criterion most likely to be got wrong.** The tempting implementation aborts the
recording when the audio constraint fails, so a user who wanted narration loses the entire capture
instead of losing the narration. Video-only with a visible warning is strictly better than nothing.

## AC-6: A recording that claims audio has audio

```gherkin
Given "Computer audio" was selected and the recording started without warning
When the recording is saved
Then the stream genuinely carried an audio track while recording
```

The failure this prevents is the quiet one: `getDisplayMedia` accepting the request, returning no
audio track, and the app reporting success. The user discovers it only on playback, after the
moment has passed. Check `stream.getAudioTracks().length` after acquisition and surface the truth
either way.

## AC-7: The existing pipeline is undisturbed

```gherkin
Given audio has been added
When a recording is made
Then the streaming save path, atomic .part rename, quality presets, frame rate and the library
  all behave exactly as before
And `npm run verify:guards` still passes
```

  <files>src/shared/types.ts, src/main/index.ts</files>
  <action>
    Types first in `src/shared/types.ts`:
    - `AudioMode = 'none' | 'system'` — the two modes this plan ships. `'microphone'` and `'both'`
      arrive in 03-02; do not declare them yet, since a mode the UI offers but the code cannot
      honour is worse than one that is absent.
    - `DEFAULT_AUDIO_MODE: AudioMode = 'none'` — matches today's behaviour, so an existing user's
      recordings do not silently change.
    - An `isAudioMode` guard, mirroring `isQualityPreset`.

    **Settings schema, version 2** (`src/main/index.ts`):
    - Bump `SETTINGS_VERSION` to 2 and add `audio` to `SettingsFile`.
    - The read path must accept a **version 1 file** — the one currently on disk — keeping its
      quality preset and defaulting audio to `'none'`, then rewriting at version 2. Handle it in
      the same place that already heals absent/corrupt files, so there is one recovery path rather
      than two.
    - Reuse the existing serialized atomic write. Do not add a second settings file.

    **Loopback in the handler.** `registerDisplayMediaHandler()` currently returns
    `{ video: source, audio: undefined }`. It must return `audio: 'loopback'` when the renderer's
    request asks for audio, and `undefined` otherwise — read `request.audioRequested` rather than
    reading the setting in main. The renderer owns the decision; main honours what was asked.

    Per CLAUDE.md, `'loopback'` is what gives real WASAPI system audio on Windows. Note in a comment
    that this is Windows-specific behaviour.

    **IPC:** `settings:get-audio` and `settings:set-audio`, validating with the guard before writing,
    mirroring the quality handlers exactly.

    Avoid: a second settings file, a second recovery path, and reading renderer state in main.
  </action>

  <action>
    **Preload:** `getAudioMode()` / `setAudioMode(mode)`, typed from shared, named surface as always.

    **useRecorder** — read the audio mode at `start()`, beside the quality preset, so a change
    applies to the next recording without a restart and is held for the duration.

    - `'none'`: call `getDisplayMedia` with `audio: false`, exactly as today. The resulting stream
      has no audio track, so `MediaRecorder` writes none (AC-2).
    - `'system'`: request `audio: true`. Main answers with `'loopback'`.

    **After acquisition, check what actually arrived** (AC-6):

      rather than the request.

    **If acquisition throws entirely while audio was requested**, retry once with `audio: false`
    before giving up. A driver that refuses audio capture should cost the narration, not the
    recording. Only a video failure is fatal.

    Avoid: treating an audio failure as a recording failure, and reporting success on a stream whose
    audio track never arrived.

<boundaries>

## DO NOT CHANGE

- Streaming save pipeline: `recordings:begin` / `append` / `finish` / `abort`
- `.part` atomic write, `recoverOrphanedParts()`
- Capture video path: `getDisplayMedia`, `resizeMode: 'none'`, 60 fps target
- Codec preference (webm/vp9 first) — VP9 carries Opus audio; changing it affects both
- Quality preset model — extended here, not replaced
- `recordingPath.cjs` validation and `verify-guards.cjs`
- The CSP. Audio needs no new source.
- `webPreferences` — `contextIsolation: true`, `nodeIntegration: false`
- `package.json` — no `"type": "module"`; `typescript` pinned at 5.9.3

## SCOPE LIMITS

- System audio only. Microphone, mixing and level control are 03-02.
- No per-source volume, no meters, no monitoring.
- No audio-only recording mode.
- No window or region selection, no thumbnails.
- No new runtime dependencies.

## AUDIT-ENFORCED INVARIANTS (carried)

- A subsystem failing must not destroy the user's primary artifact
- Report what happened, never what was requested
- Settings reads never throw; a corrupt or old file heals itself
- Every handler taking a path validates containment

</boundaries>
